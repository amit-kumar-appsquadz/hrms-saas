## Reserved-label list

`app`, `www`, `platform`, `admin`, `api`, `static` (config: `tenancy.reserved_labels`).

- The apex/base host `app.example.com` resolves to **no tenant** (platform/base host).
- Each reserved label as a leftmost subdomain (`platform.app.example.com`, etc.)
  resolves to **no tenant** — never an attempt to look up a tenant named `platform`.
- `admin` is reserved as defence-in-depth so no tenant can ever claim it; there is
  deliberately **no admin host** (ADR-007 decision 2). Reserving the label is not
  an admin-host declaration.

## Resolution behaviour (acceptance matrix)

| Host | Result |
|---|---|
| `acme.app.example.com` (serveable) | tenant `acme` bound into context |
| `app.example.com` (base/apex) | no tenant; request continues |
| reserved label `*.app.example.com` | no tenant; request continues |
| unknown `<x>.app.example.com` | `404 tenant_unavailable` (non-enumerating) |
| `suspended`/`provisioning`/`inactive` tenant | `404 tenant_unavailable` (identical to unknown) |
| nested `a.b.app.example.com` / unrelated host | no tenant (not guessed) |

## Fail-closed decision

Fail-closed is the core isolation guarantee (ADR-001 amendment, ADR-007 §1). The
middleware **never** selects a default tenant.

- A base/reserved/unrelated host leaves `TenantContext` **empty**. In the default
  (tolerant) mode the request continues with no tenant — this is correct for the
  platform plane and for base-host tenant login, where the tenant is established
  later from the authenticated session, not from the host.
- The strict mode `resolve.tenant:required` is for tenant-scoped routes: with no
  resolvable tenant it returns `400 tenant_required`. It never defaults.
- Downstream, `TenantContext::requireTenantId()` throws when empty, so even a
  tolerant-mode request that reaches tenant-scoped data (global scope / guard,
  B1-06/B1-07) fails closed rather than widening a query to all tenants.
- An unknown subdomain and a non-serveable tenant return the **identical**
  `404 tenant_unavailable` body, so an attacker cannot tell whether a tenant
  exists (non-enumerating). Status gating reads `tenants.status` (ADR-008):
  only `trial` and `active` are serveable; `provisioning/suspended/inactive`
  are refused.

The host is **routing only** and is not trusted as the security boundary — that
remains identity + token audience + permission namespace + resolved tenant
context (ADR-007 §1), enforced by the guards in B1-03/B1-07. This middleware only
maps host → tenant/no-tenant without ever guessing.

## How the TenantConnectionResolver seam works

ADR-001 keeps a single `TenantConnectionResolver` abstraction so an enterprise
tenant can later be routed to a dedicated database without touching call sites.

- `connectionFor($tenant)` is the one entry point. Phase 1 (flag
  `dedicatedPlacementEnabled = false`) **always** returns the shared/default
  connection (`config('database.default')`) regardless of tenant.
- The `tenants.db_connection` nullable placement column (owned by B1-01) is the
  seam. `placementFor($tenant)` reads it; `connectionFor()` would return it when
  the flag is enabled and dedicated connections are wired into
  `config/database.php`. Flipping to real dedicated routing is a config + a
  single-method change here — never a change at call sites.
- `ResolveTenant` calls `connectionFor()` on the success path so the seam is
  exercised live (returns shared in Phase 1). The resolver is not a security
  boundary: a dedicated-DB tenant still carries `tenant_id` + the global scope.

## Integration assumption (B1-01 parallel-wave dependency)

B1-05 does **not** define the `tenants` migration or `Tenant` model — those are
B1-01, running in the same wave. B1-05 codes against `App\Models\Tenant` /
`tenants` **by name** through `TenantResolver`. In this worktree B1-01 is not
present, so `TenantResolver::tenantsTableAvailable()` returns false and all
tenant lookups fail closed (`tenant_unavailable`), which the seam test asserts.
When B1-01 lands, the model/table become resolvable and real tenants resolve with
**no code change** here. The status values read (`trial/active` serveable;
`provisioning/suspended/inactive` refused) match ADR-008 exactly (no `pending`).

## Risks / follow-ups

- B1-05 provides the `resolve.tenant` alias but does **not** attach it to the
  global `tenant` middleware group. Composing resolution + audience + context into
  the tenant group is B1-07's job (so the guard can enforce `required` fail-closed
  on real routes). Until then, resolution is opt-in per route/group.
- Status enum coupling: `config/tenancy.serveable_statuses` mirrors ADR-008. If
  ADR-008's serveable set changes, update the config. QA B1-13 re-asserts the
  status gate against B1-01's real enum.
- `base_domain` is env-configurable (`TENANCY_BASE_DOMAIN`); prod must set it to
  the real base host. Custom-domain CNAME mapping is out of scope (ADR-001).
- Nested/unknown hosts fail closed by design; if a future dev setup needs a
  non-`app.example.com` base host, set `TENANCY_BASE_DOMAIN` accordingly.
