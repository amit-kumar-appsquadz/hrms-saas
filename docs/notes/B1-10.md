## Scope guard (human decision E-1)
B1 is **FOUNDATIONS ONLY**. This task builds the `platform_access_sessions` **table** + the read-only session **STATE/validation model** only. There is **NO** live tenant-token minting, **NO** write impersonation, and **NO** code path that issues a usable tenant access credential. Live read-only access-session token issuance + runtime behaviour + double-audit wiring are **B3 behind SEC-3**. The model proves the SHAPE + invariants of the single hardened cross-plane read path (ADR-007 §6); it does not operate it.

## What changed
- **Migration** `backend/database/migrations/2025_01_01_000200_create_platform_access_sessions_table.php`
  - Columns: `id, platform_user_id, tenant_id, mode('read_only'), reason, started_at, expires_at, ended_at, request_id, timestamps`.
  - `mode` is a single-value `enum(['read_only'])` so the storage layer itself refuses any other mode.
  - Indexes on `platform_user_id`, `tenant_id`, `expires_at`, `request_id` — **not** tenant-first composite indexes, because this platform-owned table has no tenancy dimension.
  - **No `token`/`secret`/`access_token`/`jwt` column** — nothing persists a usable credential in B1.
  - FKs to `platform_users` and `tenants` + CHECK constraints (mode, TTL) are added **only on server drivers (MySQL/MariaDB/Postgres)** and **only when the referenced table exists** (see Integration assumption). SQLite (the test driver) can't `ALTER ... ADD FK/CHECK` after create, so there the invariants are proven at the model + test layer.
- **Model** `backend/app/Platform/AccessSession.php`
  - Plain Eloquent model, table `platform_access_sessions`. **No `BelongsToTenant`**, no global scope.
  - `AccessSession::start(platformUserId, tenantId, reason, startedAt?, requestedExpiry?, requestId?)` is the single validated construction entry point. Returns the **STATE object** (never a token). Not persisted until `->save()`.
  - `booted()->saving()` guard re-applies the invariants on every persist regardless of how the row was built.
  - Helpers `isActive()`, `remainingSeconds()`.
  - Constants `MODE_READ_ONLY='read_only'`, `MAX_TTL_MINUTES=15`.
- **Factory** `backend/database/factories/Platform/AccessSessionFactory.php` — valid sessions by default; `requestingOverCapTtl()` + `ended()` states. Creates no token.
- **Tests** `backend/tests/Feature/Platform/AccessSessionTest.php` (18) and `AccessSessionNoMintingTest.php` (4).

## Invariants and how each is enforced
1. **`mode` fixed to `read_only`.**
   - DB: single-value `enum(['read_only'])` + named CHECK `chk_pas_mode` on server drivers.
   - Model: not mass-assignable; `start()` sets it to `MODE_READ_ONLY`; the `saving` guard **forces** it back to `read_only` even if a caller overwrites the attribute. No write/full/impersonate mode constant exists (asserted by test).
2. **TTL ≤ 15 min (`expires_at ≤ started_at + 15 min`).**
   - **Decision: CLAMP, not reject.** A requested expiry beyond the cap is silently reduced to `started_at + 15 min` (never extended); a sub-cap request is preserved; the default is the cap. Rationale below.
   - Model: `resolveCappedExpiry()` in `start()` and the `saving` guard (`clampExpiry()`).
   - DB: named CHECK `chk_pas_ttl` on server drivers as belt-and-suspenders.
3. **`reason` required, non-empty.**
   - DB: `reason` is `NOT NULL`.
   - Model: `assertReasonPresent()` rejects null/empty/whitespace-only in both `start()` and the `saving` guard (throws `InvalidArgumentException`).
4. **Platform-owned, FK-not-discriminator (ADR-007 §8).**
   - No `BelongsToTenant`, no implicit `where` on a fresh query (asserted). `tenant_id` is a plain FK to `tenants.id` (the TARGET tenant), not the ADR-001 scope key — rows for many target tenants coexist and are all visible from one platform-plane query (asserted).

### TTL cap decision: reject vs clamp
**Chosen: clamp (reduce) to the 15-minute cap.** Reasons: (a) the invariant that matters for safety is "a session can never outlive 15 minutes" — clamping guarantees it unconditionally; (b) it is fail-safe (a caller mistake shortens, never extends, access); (c) it avoids a usability footgun where a slightly-too-long request would hard-fail. A longer TTL is therefore **refused in effect** (never granted) while the session still starts. The DB CHECK additionally makes an over-cap row impossible on server drivers, so even a bypass of the model cannot persist a >15-min window.

## No token minting / no write impersonation (why + how asserted)
Per E-1 and ADR-007 §6, B1 exposes **no** path that mints a tenant token or performs write impersonation. `AccessSessionNoMintingTest` is a tripwire:
- no method declared on `AccessSession` whose name contains `mint`, `issuetoken`, `accesstoken`, `tenanttoken`, `impersonate`, `assume`, `elevate`, `escalate`, etc.;
- the model does **not** use `Laravel\Sanctum\HasApiTokens` (would add `createToken`);
- `start()` returns the model STATE only and the state carries no `token`/`secret` attribute;
- the only mode is `read_only`.
Minting + double-audit (`platform_audit_logs` via B1-09 + tenant trail) are deferred to **B3/SEC-3**.

## Integration assumption (FK guarding)
Base worktree is `agent/B1-02`, which has `platform_users` but **not** `tenants` (that ships in B1-01). The migration creates both FK columns always, but adds the actual FK constraints **only when the referenced table is present** and only on server drivers. So the migration runs cleanly in this worktree and the real FKs to `tenants` (and `platform_users`) resolve when B1-01/B1-02 are merged into `sprint/<N>` on MySQL. On SQLite there are no post-create FKs by design; the relationships are exercised at the model/test layer.

## B3 / SEC-3 deferral
Deferred out of B1: live read-only tenant-context token issuance (audience `tenant`, `platform_access=true`, `platform_actor` claim, `exp ≤ 15 min`), the `POST /platform/tenants/{tenantId}/access-sessions` + `DELETE .../{id}` runtime, the persistent "platform/support access — read only" tenant banner, and the double-audit write. These are B3 behind SEC-3 and are **not** in the contract as "done".

## Risks
- **SQLite vs MySQL enforcement gap:** on SQLite the FK/CHECK constraints are not present; the model guards + tests carry the invariants there. On the real MySQL path the DB also enforces them. Risk is low because the model guard runs on every `saving`.
- **Clamp hides caller intent:** a caller asking for 60 min silently gets 15. Documented and intentional (fail-safe). B3 should surface the effective TTL in the API response.
- **FK resolution depends on merge order:** if `tenants` is absent at migrate time on a server driver, the `tenant_id` FK is skipped (column still created). Re-running after B1-01 lands requires the FK to be present — handled naturally when the sprint branch has all tasks; a follow-up migration is not needed within B1 because the sprint integration migrates fresh.
