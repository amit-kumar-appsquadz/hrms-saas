# B1-07 — Tenant auth guard + `tenant` audience

Wave 2 (final task). Depends on **B1-05** (`TenantContext` + `ResolveTenant`) and
reuses the **B1-03** `TokenAudience` primitive (`platform`/`tenant` enum + HMAC
token). Implements the TENANT-plane authentication guard: it authenticates tenant
`users` **within the resolved tenant context**, issues/verifies tokens with
audience `tenant`, and **rejects `platform`-audience tokens** (ADR-007 §1, §3;
ADR-001). Foundations only — no login UX/MFA (that is B2/B3).

## The audience + context double-check (how the boundary is enforced)

`TenantGuard::user()` resolves a request to a tenant user only if ALL hold, in
order (ADR-007 §1):

1. **Token verifies** (`TokenAudience::verify`) — HMAC signature valid.
2. **Audience is `tenant`** (`TokenAudience::TENANT->matches($claims)`). A
   `platform`-audience token is rejected here regardless of path/host — this is
   the "reject platform tokens" acceptance.
3. **A tenant is resolved** in `TenantContext` (`hasTenant()`); otherwise **fail
   closed** — the guard never authenticates against "all tenants".
4. **Optional `tid` claim must match** the resolved tenant id (a tenant-A token
   replayed in tenant B is rejected on the claim alone, before any DB hit).
5. **Identity store, tenant-scoped**: the subject (`sub`) is looked up ONLY in
   the tenant-owned `users` table **filtered by the resolved `tenant_id`**.
6. **Double check**: the loaded row's `tenant_id` is re-compared to the context's
   tenant id (redundant with step 5 by design — defence against a future
   scope-bypass or trait misconfiguration).
7. **Status gate**: only `status = active` tenant users may authenticate (stub;
   full lifecycle is B2).

## How cross-tenant authentication is rejected

- The DB lookup is `where('tenant_id', <resolvedTenantId>)->whereKey(<sub>)`, so a
  user id from tenant B simply does not resolve in tenant A's context (step 5),
  and the row's `tenant_id` is re-validated against the context (step 6).
- The same email can exist in two tenants (per-tenant `UNIQUE(tenant_id, email)`);
  each identity authenticates only within its own tenant — proved by test
  `same_email_may_exist_in_two_tenants`.
- No resolved tenant ⇒ rejected (step 3). This does **not** rely on B1-06's global
  scope, so isolation holds today in this base branch.

## Security notes (SEC-1 relevant)

- Boundary is **server-side** (audience + identity store + tenant context), not
  URL/host — a platform token on a tenant route is rejected by the guard itself.
- SEPARATE identity stores: `tenant_users`/`App\Models\Tenant\TenantUser` vs
  `platform_users`/`App\Models\Platform\PlatformUser`. **No shared/universal user
  table.** No FK between the two.
- Fail-closed everywhere: missing/malformed token, wrong audience, no tenant
  context, cross-tenant subject, non-active status → all rejected (null user →
  401/400). No default tenant is ever selected.
- `tenant_id` is server-derived (context), never client-supplied.

## Risks / caveats

- The `users` table is now **tenant-owned** (global `UNIQUE(email)` dropped in
  favour of `UNIQUE(tenant_id, email)`). The generic scaffold `App\Models\User`
  and its `UserFactory` were left in place but are effectively superseded for the
  tenant plane; B2 should consolidate on `App\Models\Tenant\TenantUser`. If B1-03
  (which uses `User::factory()` in its tests to represent a *tenant* user) is
  merged alongside, its factory calls will need a `tenant_id` — a merge-time
  reconciliation for the sprint integrator, not a conflict in this worktree.
- No FK from `users.tenant_id` to `tenants.id` yet (B1-01 not present); the column
  + composite index satisfy tenancy. The FK can be hardened when B1-01/B4 land.
- The B1 token primitive is HMAC-over-`APP_KEY`, test-only by design (B1_PLAN §0);
  not the production scheme.
