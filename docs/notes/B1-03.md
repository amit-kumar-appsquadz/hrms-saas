## Audience mechanism (the plane boundary)

ADR-007 §1 enforces the boundary **server-side, in order**: identity store → token audience → authorization namespace → tenant context → explicit checks. B1-03 implements the first three for the platform plane:

1. **Identity store.** The `platform` guard resolves the token subject **only** through the `platform_users` provider. A tenant `users` row never resolves here even with a validly-signed token.
2. **Token audience.** Every token carries an `aud` claim. `PlatformGuard` rejects anything whose `aud` ≠ `platform`. This is **path/host independent**: a `tenant`-audience token presented to a `/api/v1/platform/*` route is rejected on the audience alone (proven by `PlatformAudienceMiddlewareTest`).
3. **Authorization namespace.** `AuthorizePlatform` maps the user's fixed role → `platform.*` permissions via `PlatformAuthorizer` and authorizes the specific permission. The authorizer carries **no** `tenant.*`.

Token primitive is deliberately minimal (HMAC with `APP_KEY`, no new dependency, no cloud calls) — this is the B1 **foundation**. Full login/MFA token issuance (Sanctum/JWT) is B2; the `aud` claim + `TokenAudience::verify()` contract is the stable seam.

## Role → permission map (Phase 1, fixed)

| Role | `platform.*` permissions |
|---|---|
| `PLATFORM_SUPER_ADMIN` | all 13 catalog permissions |
| `PLATFORM_OPERATIONS` | dashboard.view, tenant.view/create/edit/activate/suspend/access, audit.view, settings.view |
| `PLATFORM_SUPPORT` | dashboard.view, tenant.view, tenant.access, audit.view |
| `PLATFORM_AUDITOR` | dashboard.view, tenant.view, audit.view, settings.view (read-only) |

Catalog (`PlatformAuthorizer::PLATFORM_PERMISSION_CATALOG`): `platform.dashboard.view`, `platform.tenant.view`, `platform.tenant.create`, `platform.tenant.edit`, `platform.tenant.activate`, `platform.tenant.suspend`, `platform.tenant.access`, `platform.user.view`, `platform.user.manage`, `platform.audit.view`, `platform.settings.view`, `platform.settings.manage`, `platform.billing.manage`.

## Disjointness guarantee (`platform.*` ∩ `tenant.*` = ∅)

`PlatformAuthorizer::namespacesAreDisjoint()` asserts `array_intersect(PLATFORM_PERMISSION_CATALOG, TENANT_PERMISSION_CATALOG) === []`. The guarantee is also **structural**: every platform permission is prefixed `platform.` and every tenant permission `tenant.`, so the sets cannot intersect regardless of the tenant list's completeness. The `tenant.*` catalog here is a **declared mirror** for the proof only — the authoritative tenant RBAC lives on the tenant plane (B2/B3) and is never consulted for a platform decision. (`PlatformAuthorizerTest::test_platform_and_tenant_permission_sets_are_disjoint`.)

## Extension seam (documented, NOT built)

There is **no `platform_roles` table** (ADR-007 §4). To add configurable platform RBAC later: replace the body of `PlatformAuthorizer::permissionsFor()` with a table/repository lookup seeded from the current in-code map. Call sites go through `roleCan()` / the `platform.authorize` middleware and never read the enum map directly, so no call site changes.

## Risks / notes
- The B1 token primitive is HMAC-only and intentionally not production-grade (no rotation, no expiry enforcement beyond an `iat` claim). B2 replaces it; the `aud` contract is preserved. **Not** a secret and not committed — it uses the app key at runtime.
- `platform_users` and `users` currently share an auto-increment id space (separate tables). The guard still cannot cross planes because it resolves subjects against the platform provider **and** checks the audience; the wrong-store test confirms a tenant user id does not authenticate.
- The two `/_probe*` routes are test-only seams in the platform plane; they must be removed/replaced when real B2 endpoints land (left in place so SEC-1/QA can exercise the live middleware).
- The two B1-02 test-assertion edits are the only change to another task's files, forced by the enum-cast switch this task owns.
