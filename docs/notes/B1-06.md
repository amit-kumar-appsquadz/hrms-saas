## Fail-closed decision (CRITICAL)

"No resolved tenant" must NEVER mean "all tenants' rows". The chosen behaviour is **throw, not widen**:

- The global scope (`TenantScope::apply`) calls `TenantContext::requireTenantId()`, which throws `TenantResolutionException` when no tenant is resolved. The scope never emits an un-filtered query and never scopes to `null`.
- Insert (`creating` hook) also calls `requireTenantId()`, so a row can never be written with a NULL/absent `tenant_id`.
- Cache-key building (`TenantCacheKey::prefix()/key()`) also calls `requireTenantId()`, so a cache key can never be produced without a tenant prefix (which would let two tenants collide on one key).

Rationale: an exception surfaces the programming/routing error loudly at the point of misuse, whereas returning all rows (or scoping to null, or returning an un-prefixed key) would be a silent cross-tenant leak. This matches `TenantContext`'s documented fail-closed contract and the B1-05 `ResolveTenant` strict mode.

Insert also refuses an **explicit mismatched** `tenant_id`: if calling code sets `tenant_id` to a value other than the current tenant, the `creating` hook throws (attempted cross-tenant write). An explicit value equal to the current tenant is allowed; the common path leaves it unset and it is auto-filled.

## Scope-bypass mechanism (and why it's safe)

The ONLY sanctioned cross-tenant path is `BelongsToTenant::withoutTenantScope()` — a thin, named wrapper over Eloquent's `withoutGlobalScope(TenantScope::class)`.

Why this is safe and auditable:
- It is a **named** method, so every bypass is greppable (`withoutTenantScope`) for the SEC review — unlike raw `withoutGlobalScope()` calls scattered around the codebase.
- Steering rule 2 / ADR-001 require every call site to carry an inline comment justifying why crossing tenants is correct AND a dedicated test. The trait's docblock states this requirement; the test `test_explicit_bypass_sees_all_tenants` is the reference call site + test.
- There is **no implicit bypass anywhere else**: absent this explicit call, the scope always applies. The bypass intentionally does not call `requireTenantId()` (an administrative cross-tenant read legitimately runs without a single tenant context), which is why it is explicit and must be justified per call site.

No bypass call sites exist in product code in B1-06 — only the test exercises the path.

## Cache-key scheme

`t:{tenant_id}:{key}` using the **surrogate `tenant_id`** from `TenantContext` (not the subdomain slug), per ADR-001's resolved open question (surrogate is stable, never reused). Helpers:
- `TenantCacheKey::prefix()` / `key($k)` — current tenant, fail-closed.
- `TenantCacheKey::prefixFor($id)` / `keyFor($id,$k)` — static, for code paths that legitimately carry their own tenant id (e.g. queued jobs).
- `BelongsToTenant::tenantCacheKey($k)` — model convenience delegating to `TenantCacheKey`.

## Tenancy shape of the fixture

`tenant_pings` carries a non-null `tenant_id` and a composite index starting with `tenant_id` (`index(['tenant_id','label'])`), per ADR-001's index strategy. The model uses `BelongsToTenant` and ships with a factory (steering: every tenant table has a factory + isolation test).

## Risks / notes

- **Auto-fill respects a pre-set equal value.** If product code sets `tenant_id` explicitly to the current tenant, it is accepted; a mismatch throws. Watch for code that sets `tenant_id` from untrusted input — prefer leaving it unset and letting the trait fill it.
- **Bypass discipline is a review item, not a mechanism.** The trait makes bypasses explicit and greppable, but it cannot force a justification comment or test — that is enforced by SEC review (B1-14). Any future `withoutTenantScope()` call in product code must be flagged.
- **Fixture is test-only.** `tenant_pings` has no production migration by design (B4 brings real tenant tables). If a future task needs a real sample table, it must add a product migration, not promote the fixture.
- **Octane.** The scope reads the request-scoped singleton `TenantContext`; B1-05 already resets it per request. No static tenant state is held in the trait/scope.
