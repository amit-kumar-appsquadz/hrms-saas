# B1-04 — Tenant lifecycle state machine (ADR-008)

## What changed

A **pure domain service** enforcing the ADR-008 tenant lifecycle, plus the two
seams it needs (platform audit, initial-admin guard) and the 409 error mapping.

New files (all under `backend/`):

- `app/Platform/TenantLifecycle.php` — the state machine. Holds the authoritative
  transition map (`TRANSITIONS`), validates transitions, runs the activation
  guard hook, mutates the `Tenant` model's `status`, and emits one platform-audit
  event per successful transition. No HTTP/DB/routing knowledge (the caller
  persists and enforces the platform-plane boundary).
- `app/Platform/TenantLifecycleException.php` — domain error. Carries an error
  `code`, maps to **HTTP 409** with the contract `Error` shape, self-renders via
  `render()`.
- `app/Platform/Audit/PlatformAuditLogStore.php` — **B1-09 seam** (interface the
  service depends on).
- `app/Platform/Audit/PlatformAuditEvent.php` — immutable audit value object
  (actor, from→to, reason, target tenant, category, action).
- `app/Platform/Audit/InMemoryPlatformAuditLogStore.php` — temporary append-only
  implementation bound until B1-09 ships the real Mongo store.
- `app/Platform/InitialAdminChecker.php` — **B4 seam** for the activation
  "initial admin exists" precondition.
- `app/Platform/StubInitialAdminChecker.php` — temporary stub (defaults to
  "admin exists"); overridable so tests can drive the guard-fails path.
- `tests/Unit/Platform/TenantLifecycleTest.php` — exhaustive transition matrix,
  guards, audit, `pending` absence.
- `tests/Feature/Platform/TenantLifecycleHttpMappingTest.php` — proves the 409 +
  contract `Error` shape over a request.

Modified:

- `app/Providers/AppServiceProvider.php` — binds the two temporary seams
  (`PlatformAuditLogStore` → in-memory singleton; `InitialAdminChecker` → stub).
- `bootstrap/app.php` — registers the `TenantLifecycleException` → 409 renderer
  (belt-and-braces alongside the exception's own `render()`).

## The transition map (authoritative, from ADR-008)

```
provisioning → trial | active        (activation; guarded)
trial        → active | suspended | inactive
active       → suspended | inactive
suspended    → active | trial | inactive
inactive     → (terminal — NO transition out)
```

- Encoded in `TenantLifecycle::TRANSITIONS`. `inactive` maps to `[]` (terminal).
- A re-signed customer is a brand-new provisioning, not a transition out of
  `inactive` (ADR-008).
- `pending` does **not** exist — not a map key, not a destination, not in
  `Tenant::STATUSES`. A unit test asserts this.
- The unit test mirrors the ADR-008 map independently and asserts
  `TenantLifecycle::TRANSITIONS` equals it, so any drift fails loudly.

## How the 409 mapping works

- An illegal transition or a failed activation guard throws
  `TenantLifecycleException` with one of three codes:
  - `tenant_lifecycle_illegal_transition` — source→destination not in the map.
  - `tenant_lifecycle_terminal_state` — any attempt to leave `inactive`.
  - `tenant_lifecycle_activation_guard_failed` — activation guard precondition
    failed.
- The exception maps to **HTTP 409 Conflict** with the contract `Error` shape
  (`openapi.yaml` → `#/components/schemas/Error`):
  ```json
  { "error": { "code": "...", "message": "...", "request_id": "..." } }
  ```
  `request_id` is included only when the request carries `X-Request-Id` (or a
  `request_id` request attribute).
- Mapping is implemented in `TenantLifecycleException::render()` and also
  registered in `bootstrap/app.php` `withExceptions()`. The service itself stays
  pure (never touches the response layer).

## Audit seam + B1-09 integration point

- The service depends only on the `PlatformAuditLogStore` interface and emits one
  `PlatformAuditEvent` per **successful** transition with: `actor`, `from`→`to`,
  `reason`, `target_tenant_id`, `category = tenant_lifecycle`,
  `action = tenant.lifecycle.transition`. No audit is written on a rejected
  transition.
- **B1-09 integration point:** B1-09 provides the real append-only MongoDB
  implementation writing to the separate `platform_audit_logs` collection
  (ADR-007 §7) and will **replace the binding** in `AppServiceProvider::register()`
  (`PlatformAuditLogStore` → Mongo store). The interface must stay append-only.
  B1-09 enriches the event with transport/context fields (request_id, ip, device,
  access_session_context) at the write point — those are not the pure service's
  concern.

## Stubbed admin-existence guard

- ADR-008 activation (`provisioning → trial|active`) requires provisioning
  complete **and** an initial admin to exist.
- The guard **hook is real and wired** in `TenantLifecycle::assertGuards()`. The
  initial-admin existence check is delegated to `InitialAdminChecker`, which is
  **stubbed** (`StubInitialAdminChecker`, defaults to "admin exists") because the
  tenant `users` table and the platform-triggered initial-admin invite do not
  exist until B4.
- A test drives `StubInitialAdminChecker(false)` to prove activation is rejected
  (409, `activation_guard_failed`) when no admin exists, and that non-activation
  transitions (e.g. `active → suspended`) are **not** gated by this check.
- **B4 integration point:** replace `StubInitialAdminChecker` with a real checker
  querying the tenant `users` table for an invited/active initial admin. The
  provisioning-complete sub-check also has a seam comment in `assertGuards()` for
  richer onboarding-progress signals.

## Security notes

- Lifecycle writes are **platform-plane only**. This service does not enforce the
  boundary itself; it is enforced when wired to endpoints in B2/B3 (platform
  audience + `platform.tenant.*` permission). It must only ever be called from
  platform context. No tenant-plane route calls it.
- The service is pure and side-effect-light: it mutates the passed model's
  `status` and emits an audit event. Persistence is the caller's responsibility.

## Risks / notes

- The in-memory audit store is process-local and NOT persistent — a temporary
  placeholder until B1-09. Nothing should rely on it for real audit durability.
- The admin-existence guard currently defaults to "exists", so in B1 activation
  always passes the admin gate. This is intentional (no tenant users yet) and
  must be revisited in B4.
- The service does not persist the model; a caller that forgets to save will not
  commit the status change. Endpoint wiring (B2/B3) must persist within the same
  request/transaction and record audit via the real B1-09 store.
- No ADR or `openapi.yaml` changed. The map matches ADR-008's "State transitions"
  section exactly (the authoritative section). The 409 body matches the contract
  `Error` schema.
