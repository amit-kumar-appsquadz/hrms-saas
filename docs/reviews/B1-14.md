## Per-item checklist

### 1. Boundary enforced SERVER-SIDE (audience + identity + namespace + context), not URL/host — PASS
- `app/Auth/TokenAudience.php`: `aud` is a signed claim; `matches()` compares the
  claim against the plane enum — path/host never consulted.
- `app/Auth/PlatformGuard.php` (`user()`): rejects non-`platform` audience
  (lines ~95-99) **before** resolving the subject, and resolves the subject only
  via a `platform_users` provider; a non-`PlatformUser` instance → null.
- `app/Auth/TenantGuard.php` (`user()`): rejects non-`tenant` audience, then
  requires a resolved `TenantContext` (fail-closed), then resolves the subject
  **scoped to `tenant_id`** with a redundant post-load `tenant_id` double-check,
  plus an optional `tid`-claim equality check.
- HTTP enforcement: `EnsurePlatformAudience` / `EnsureTenantAudience` run the
  guard and 401 on failure, independent of the route path.
- Evidence: `Sec1/TokenAudienceIsolationTest` proves BOTH directions end-to-end
  through the real middleware stack, each with a positive control (same subject +
  correct audience succeeds), so rejection is attributable to the audience alone.
  `Sec1/SeparateIdentityStoresTest` proves wrong-store rejection at the guard.

### 2. No universal/shared user table; `platform_users` and tenant `users` physically separate, no cross-plane FK — PASS
- `database/migrations/2025_01_01_000100_create_platform_users_table.php`: table
  `platform_users`, no `tenant_id`, no FK to `users`.
- `database/migrations/2025_01_01_000100_add_tenant_columns_to_users_table.php`:
  tenant `users` gets `tenant_id` + composite `UNIQUE(tenant_id,email)` +
  `INDEX(tenant_id,id)`; no `platform_user_id` column.
- Models pin distinct tables (`PlatformUser::$table='platform_users'`,
  `TenantUser::$table='users'`).
- Evidence: `Sec1/SeparateIdentityStoresTest` asserts distinct tables, absence of
  `platform_tenant_users|universal_users|all_users|identities`, absence of
  cross-plane FK columns, and that the same email in both planes is two
  independent rows.

### 3. No `platform_roles` table; platform RBAC is the fixed `PlatformRole` enum via `PlatformAuthorizer`; platform.* ∩ tenant.* = ∅ — PASS
- No `platform_roles` / `platform_role_permissions` migration exists (confirmed by
  file listing + grep). Roles are the fixed enum `app/Platform/PlatformRole.php`;
  `platform_users.platform_role` is an ENUM constrained to the four values (+ a
  named CHECK on server drivers).
- `app/Platform/PlatformAuthorizer.php` is the single code-mapped authorizer; call
  sites use `roleCan()` (see `AuthorizePlatform` middleware), never read the enum
  map directly — the documented extension seam is intact.
- Disjointness holds structurally (`platform.` vs `tenant.` prefixes).
- Evidence: `Sec1/PermissionNamespaceDisjointnessTest` asserts empty intersection,
  per-prefix membership, that no role grants any `tenant.*`, and that even
  SUPER_ADMIN is denied `tenant.payroll.manage`.

### 4. No admin host; same-domain routing only; base/reserved hosts fail closed with no default tenant — PASS
- `config/tenancy.php`: `base_domain` only; reserved labels
  `app,www,platform,admin,api,static`. `admin` is reserved **as defence-in-depth
  to guarantee no tenant can claim it** — there is no admin host declared
  anywhere (grep for `admin.app`/`admin.example` finds only ADR/notes "rejected"
  context, never config/code).
- `app/Http/Middleware/ResolveTenant.php`: base/apex and reserved labels → no
  tenant; unknown subdomain and non-serveable status return an identical
  non-enumerating 404; `:required` mode returns 400 and NEVER selects a default
  tenant. `TenantContext` starts empty and is never seeded with a default.
- Evidence: `Sec1/BaseHostFailClosedTest` (incl. a data-provider over all reserved
  labels) proves real subdomain resolves, base/reserved carry no tenant, required
  routes 400 with `tenant_required`, and the response carries no `tenant_id`.

### 5. `BelongsToTenant` global scope absolute; cross-tenant read blocked; no-tenant fails closed; only bypass is explicit, named, tested — PASS
- `app/Tenancy/TenantScope.php` + `TenantContext::requireTenantId()`: the scope
  reads the tenant via `requireTenantId()`, which **throws** when none is
  resolved — it never drops the predicate (no "no tenant = all rows"). Insert
  auto-fill likewise throws, and a mismatched explicit `tenant_id` on create is
  refused (cross-tenant write guard) in `BelongsToTenant::bootBelongsToTenant()`.
- The only bypass is the named, greppable `BelongsToTenant::withoutTenantScope()`
  with a documented "comment + dedicated test" contract.
- Evidence: `Sec1/CrossTenantReadIsolationTest` proves A can't read/list/count/
  find B's rows, that the SQL always carries a `tenant_id` predicate, that a
  cleared context **throws** (`TenantResolutionException`) rather than returning
  all rows, and that `withoutTenantScope()` is the only path that sees both
  tenants. (Note: `TenantGuard` deliberately does not depend on the global scope —
  it filters by `tenant_id` explicitly and re-checks — so tenant-user isolation
  holds even though the B1-07 `users` stub does not yet apply the trait; this is
  documented and correct for B1.)

### 6. `platform_access_sessions` has NO token-minting / write-impersonation path; read_only + ≤15 min + reason invariants enforced — PASS
- `app/Platform/AccessSession.php`: `mode` forced to `read_only` on `start()` and
  on every `saving` hook; TTL clamped to `started_at + 15 min` (never extended);
  non-empty `reason` required (whitespace rejected). No `mint/issueToken/token/
  accessToken/impersonate/assume` method; no token-bearing column in the
  migration (`...create_platform_access_sessions_table.php` has no
  token/secret/access_token column). Platform-owned: no `BelongsToTenant`, no
  tenant scope; `tenant_id` is a plain target-tenant FK.
- Evidence: `Sec1/AccessSessionStateInvariantsTest` + `AccessSessionNoMintingTest`
  assert the invariants, the absence of minting/impersonation methods (reflection
  tripwire over a broad fragment list), absence of `HasApiTokens`, and that
  `start()` returns state only.

### 7. Platform vs tenant audit are SEPARATE append-only collections; tenant audit is tenant-scoped — PASS
- `MongoPlatformAuditLogStore::COLLECTION='platform_audit_logs'` and
  `MongoAuditLogStore::COLLECTION='audit_logs'`; each store constructor **throws**
  if handed the other plane's collection. Neither store exposes update/delete/
  drop; append-only by shape. Tenant store stamps `tenant_id` from
  `requireTenantId()` on write (fail-closed) and filters by it on read
  (cross-tenant read blocked at the store).
- Evidence: `Sec1/AuditCollectionSeparationTest` proves fixed/different names,
  one-collection-only landing, cross-wiring refusal in both directions,
  tenant-scoped read isolation, and append-only (no mutator methods).

### 8. Tenant lifecycle matches ADR-008 (no `pending`); immutable unique subdomain; non-active statuses block access; illegal transition → 409 — PASS
- `app/Platform/TenantLifecycle.php` `TRANSITIONS` map matches ADR-008 exactly;
  `inactive` is terminal (empty destination list); activation guard hook wired.
  `TenantLifecycleException` maps to 409 with the contract `Error` envelope.
- `migrations/...create_tenants_table.php`: status enum
  `provisioning|trial|active|suspended|inactive` (no `pending`),
  `UNIQUE(subdomain)`, `INDEX(status)`. `Tenant` model enforces subdomain
  immutability in `updating()`. Resolver serves only `trial|active`
  (`config/tenancy.php`), non-enumerating refusal for the rest.
- Evidence: `TenantLifecycleHttpMappingTest` (409 + exact `error` envelope +
  request_id echo); full matrix on `agent/B1-13` (94 passed).

### 9. No secrets committed; B1 token primitive is a documented test-only HMAC foundation, clearly deferred to B2 — PASS
- `.env` is git-ignored and untracked; no secret patterns in application code
  (only `vendor/` third-party matches). PAN/bank/salary/Aadhaar fields are not in
  scope for B1 (no such tables yet) — nothing exposed.
- `TokenAudience` documents, in-file, that it is a test-only HMAC-over-APP_KEY
  primitive, adds no signing dependency, and that B2 swaps in the production
  scheme at the stable `verify()` seam. For B1 this is sound: it exists only to
  exercise the boundary under test, is never exposed through a real login/issuance
  endpoint (routes are probes only), and the APP_KEY is not a committed secret.

### 10. QA SEC-1 tests EXIST and are MEANINGFUL (not vacuous) — PASS
- 49 SEC-1 tests exist under `tests/Feature/Platform/Sec1/*` and
  `tests/Feature/Tenancy/Sec1/*` and run green. Spot-checked assertions are
  substantive: positive + negative controls on audience isolation; fail-closed
  proven by `expectException`; cross-tenant proven by seeding two tenants and
  asserting exact visible sets; disjointness asserted both as set-intersection
  and over the full role→permission map; minting-absence via reflection tripwire.
  These prove the claims rather than restating them.

## Findings

### LOW-1 (informational) — Activation guard stub defaults to "admin exists = true"
- **Where:** `app/Platform/StubInitialAdminChecker.php` (`$exists = true` default),
  consumed by `TenantLifecycle::assertGuards()`.
- **Observation:** The provisioning→trial/active activation guard currently passes
  the initial-admin existence check by default, because there is no tenant `users`
  admin concept until B4. The guard **hook** is real and wired; only the existence
  predicate is stubbed, and lifecycle writes are not reachable from any endpoint
  in B1 (no activate endpoint until B2/B3).
- **Why not a blocker:** No B1 code path lets an unauthorized actor drive a
  transition; the stub is explicitly documented and the fails-path is tested. It
  does not weaken any B1 invariant.
- **Remediation / owner:** B4 Backend — replace the stub with a real
  `InitialAdminChecker` that queries the tenant admin invite/user, before the
  activation endpoint goes live. Flag the activate endpoint PR for this when B2/B3
  wires it.

### LOW-2 (informational) — Test-only token primitive has no `exp`/replay handling
- **Where:** `app/Auth/TokenAudience.php` (`verify()` checks signature + `aud`
  only; no expiry/nonce).
- **Observation:** The B1 HMAC token has no `exp` verification, so a leaked B1
  token would not self-expire. This is acceptable for B1 because the primitive is
  test-only and never issued by a real endpoint.
- **Why not a blocker:** Deferred by plan to B2; no production issuance surface in
  B1.
- **Remediation / owner:** B2 Backend — the production token scheme (Sanctum/JWT)
  must enforce `exp`, short platform session lifetime (ADR-007 §3), and MFA. Keep
  the `verify()` contract as the swap seam. Carry forward into SEC-2.

### Noted integration reconciliations (reviewed, not findings)
- `TenantUserFactory`/`UserFactory` `tenant_id` default and merged
  `config/audit.php`: reviewed as benign test/config reconciliations; the tenant
  factory requires a tenant and the guard's explicit scoping does not rely on it.
- Laravel-12 vs plan-text skew: cosmetic; does not affect any invariant.
- B1_PLAN reserved-label "422" item QA flagged as unreachable in B1: correct —
  there is no tenant-create endpoint in B1, so reserved-label rejection at
  onboarding is a B2/ADR-008-onboarding concern. Reserved labels ARE enforced at
  resolution (fail-closed), which is the B1-relevant guarantee. Not a gap.
